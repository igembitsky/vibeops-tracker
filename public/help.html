VibeOps Tracker Help

← Back to board

VibeOps Tracker is a standalone app on http://localhost:4400. Issues live as one markdown file each under data/<project>/issues/ in the tracker repo, so you and your agents can read and grep them. Projects' own repos contain one line of tracker-related code: the widget script tag.

Install on a new project

1. Add one script tag to the project's frontend HTML (any framework, or none):

<script src="http://localhost:4400/widget.js" data-project="my-project" defer></script>

That's the whole install. A floating 🐞 button appears; submitting the dialog posts the issue here with an automatic context snapshot: what you're looking at (URL, viewport, highlighted text) is always attached. The activity trail (last 10 clicks, last 10 fetches, recent JS errors and failed requests) is a dialog checkbox, on by default for bugs and off for other types. The project key auto-registers on first capture. If the button ever covers something, drag it up or down: it stays pinned to the right edge and remembers where you put it.

2. Recommended: tell the tracker where the project's repo lives, so generated prompts point agents at the right working directory:

curl -X POST http://localhost:4400/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"key": "my-project", "name": "My Project", "repo_path": "/absolute/path/to/repo"}'

3. Optional: enrich captures with app state and git info (handy for worktree workflows, since captures then record which branch/worktree they came from):

<script>
  window.IssueTracker.configure({
    context: () => ({
      // anything useful: current tab, selected record, feature flags…
      git: { branch: "...", commit: "...", worktree: "..." }  // if the host can know it
    })
  });
</script>

Disable / Enable / Remove

Disable temporarily

Comment out the script tag (the only integration point), or just stop the tracker server. The widget fails safe and never breaks the host app:

<!-- <script src="http://localhost:4400/widget.js" data-project="my-project" defer></script> -->

Enable / re-enable

Uncomment (or re-add) the script tag, and make sure VibeOps Tracker is running: cd /path/to/vibeops-tracker && npm start (or npx vibeops-tracker).

Remove completely

Delete the script tag and any window.IssueTracker.configure block from the project. Nothing else lives in the project. The project's issues stay safely in the tracker's data/ dir; sweep or ignore them as you like.

Set up agent access (MCP)

Register once (user scope = available in every project's Claude Code sessions):

claude mcp add vibeops -- npx -y -p vibeops-tracker vibeops-mcp

Tools: get_tracker_instructions (the workflow doctrine, which agents should call first), list_projects, list_issues, search_issues, get_issue, create_issue, update_issue, add_comment, resolve_issue, delete_issue (permanent, requires confirm: true). The MCP server reads the markdown files directly, so it works even when the web server is down.

Ways to use it

Manual capture → paste into a session

  1. Hit the 🐞 button in any app when something is off; describe seeing/expecting; submit. Tip: highlight the exact text you're talking about before hitting 🐞, and it's attached to the report (previewed in the dialog, removable) and quoted prominently in the agent prompt. For non-bug reports the click/network/error trail is left off by default; tick "Include activity trail" if it matters.
  2. On the board, prioritize by dragging cards (order is saved into each issue's file).
  3. Open a card → Copy Prompt → paste into a Claude Code session in that project. The prompt carries the full issue, context summary, repo path, and the API workflow (in-progress → resolve → in-review).
  4. When the agent resolves, the card shows up in In Review with a PR-style resolution and the list of files it touched. Verify, drag to Done, and occasionally Sweep the Done column into the Archive.

Agent-driven (MCP)

With the MCP server registered, you don't need to copy anything. Just tell any session what to do (see prompts below). Agents can also file issues themselves mid-task when they notice something out of scope.

Filing without a frontend

+ New issue on the board, or create_issue via MCP, or plain curl:

curl -X POST http://localhost:4400/api/issues -H 'Content-Type: application/json' \
  -d '{"project": "my-project", "title": "...", "type": "feature", "seeing": "...", "expecting": "..."}'

Ready-made agent prompts

Paste these into a Claude Code session running in the relevant project. Click a block to select it.

Install the widget in this project

Install the issue-tracker capture widget into this project's frontend. Add
<script src="http://localhost:4400/widget.js" data-project="<project-key>" defer></script>
to the main HTML page(s), choosing a short kebab-case project key. Then register the repo path:
curl -X POST http://localhost:4400/api/projects -H 'Content-Type: application/json' -d '{"key": "<project-key>", "name": "<Readable Name>", "repo_path": "<absolute repo path>"}'
If the app knows its own state (current view, record ids, git branch), also add a
window.IssueTracker.configure({ context: () => ({...}) }) block to enrich captures.
Verify by loading the app and checking the 🐞 button appears bottom-right.

Disable or remove the widget from this project

Remove the issue-tracker widget from this project: find and delete the script tag that loads
http://localhost:4400/widget.js (and any window.IssueTracker.configure block next to it).
To disable temporarily instead of removing, comment the tag out. Make no other changes.

Pick up the next ticket and work it

You have access to my issue tracker via the issue-tracker MCP server. Call
get_tracker_instructions first, then list_issues for project "<project-key>" with status
"backlog" and pick the FIRST one (it's the highest priority). Read it fully with get_issue,
reproduce from the captured context, mark it in-progress, fix it, and finish with
resolve_issue (resolution summary + modified files). Then stop for my review. Do not pick
up another ticket unless I say so.

Triage what's on the board

Using the issue-tracker MCP server, list all issues for project "<project-key>" and give me
a triage: which backlog items look quick vs. deep, anything that's probably a duplicate
(use search_issues), anything in-review waiting on me, and what you'd tackle first and why.
Don't change anything yet.

Migrate a roadmap / TODO file into the tracker

This project has roadmap/TODO files (ROADMAP.md, TODO.md, or similar; find them). Migrate
their open items into my issue tracker via the issue-tracker MCP server (or curl to
http://localhost:4400/api/issues if MCP is unavailable):
1. Call get_tracker_instructions, then search_issues per item to skip anything already filed.
2. For each open item, create_issue with project "<project-key>": title = the item;
   seeing = current state/why it matters (quote the source file and line); expecting = done
   criteria as concretely as the source allows; type = feature/improvement/bug as appropriate;
   severity from any priority markers (default 3); tags = ["roadmap"] or ["todo"] plus topical tags.
3. Keep one issue per actionable item. Split grouped bullets, skip completed ones.
4. When finished, report a table of created ids → titles, then UPDATE the source files: mark
   migrated items with their new issue id (e.g. "→ tracked as <id>") instead of deleting them.
Do not start working on any of the issues.

Things to be aware of

  • The tracker must be running for captures, the board, and Copy Prompt: npm start in the tracker repo (the MCP tools work even without it).
  • Capture-time context goes stale. Snapshots record the branch/worktree/port at capture time; by pickup time the repo may have moved on. Prompts and instructions tell agents to verify against current state.
  • Issue files are the source of truth, stored under data/ on your machine. That directory is gitignored, so it holds real local tracker data that isn't versioned with the code, which means deletes are permanent (no git history to restore from). Don't hand-edit while the server is mid-write; prefer the API/MCP (agents are told this).
  • Deletion is manual and permanent. Open any issue and use Delete issue in the drawer's Danger zone (two-step confirm) to remove stale, test, or junk issues for good. This works on archived issues too. Agents can delete as well, via the MCP delete_issue tool (guarded by a required confirm: true flag); the doctrine tells them to reserve it for clearly stale/test/duplicate issues. For real issues you've resolved, prefer Done → Sweep to the Archive over deleting; link duplicates with related_to.
  • Icebox vs Archive. The Icebox parks a backlog item off the board when it isn't the right time to build it. Open the issue and click Send to Icebox, then Bring back from the Icebox view to return it to the Backlog. Iceboxed items also drop off agents' list_issues. The Archive is different: a read-only history of work you swept from Done.
  • Statuses: backlog → in-progress → in-review → done. Agents never set done; that's your verification step.
  • localhost-only by design. The API has no auth and allows any origin, so don't expose port 4400 beyond your machine.
